# Персональная база знаний – сравнение архитектур

Проект доступен в двух вариантах:

- **knowledge-base-pattern** – с использованием паттерна «Дополнительный модуль» (Plugin).
- **knowledge-base-monolith** – вся функциональность жёстко встроена в ядро.

## Паттерн «Дополнительный модуль» (Plugin)

Определяет интерфейс `Plugin`, который реализуют подключаемые JAR-модули.  
Ядро приложения загружает их динамически через `ServiceLoader` из папки `plugins/`.

### Преимущества

1. **Расширяемость без изменения ядра**  
   Новые функции (например, синхронизация с облаком, переводчик) добавляются простой установкой JAR в папку. Не нужно трогать код основного приложения.

2. **Изоляция зависимостей**  
   Каждый плагин может использовать свои библиотеки (PDFBox, Commonmark), которые не загромождают ядро. Это уменьшает размер базового дистрибутива и предотвращает конфликты версий.

3. **Параллельная разработка**  
   Разные команды могут создавать плагины независимо, соблюдая лишь интерфейс. Ядро остаётся стабильным, а функциональность наращивается модульно.

4. **Гибкость конфигурации**  
   Пользователь сам выбирает, какие плагины ему нужны. Ненужные можно просто удалить из папки, и они не будут влиять на производительность или интерфейс.

5. **Упрощённое тестирование**  
   Плагины тестируются изолированно. Регрессионное тестирование ядра не требует проверки всех мыслимых комбинаций расширений.

6. **Снижение порога входа**  
   Сторонние разработчики могут создавать расширения, не разбираясь во внутреннем устройстве всей системы – достаточно реализовать предоставленный контракт.

7. **Устойчивость к ошибкам**  
   Ошибка в одном плагине не должна ронять всё приложение (при аккуратной реализации загрузчика). Ядро может продолжить работу без сбойного модуля.

## Монолитный подход (без плагинов)

В этом варианте все функции (экспорт в PDF, импорт Markdown, автотегирование) находятся прямо внутри `MainFrame`. Для добавления нового функционала нужно модифицировать и пересобирать всё приложение.

### Недостатки монолита

- **Сложность расширения** – любое изменение требует правки основного кода, его перекомпиляции и перезапуска.
- **Раздувание ядра** – все зависимости и код живут в одном проекте, увеличивая его размер и время сборки.
- **Высокая связность** – изменение одной фичи может затронуть другие из-за отсутствия чётких интерфейсов.
- **Ограниченная гибкость** – конечный пользователь не может отключить ненужные функции; для кастомизации приходится лезть в исходники.
- **Сложность командной работы** – разработчики вынуждены координироваться вокруг единой кодовой базы, что замедляет процесс.

## Сравнительная таблица

| Критерий                    | Плагинная архитектура                      | Монолит                     |
|-----------------------------|--------------------------------------------|-----------------------------|
| Добавление новой функции   | JAR в папку `plugins`, без пересборки ядра | Изменение кода, новая сборка |
| Изоляция зависимостей      | У каждого плагина свои библиотеки          | Все зависимости в одном pom |
| Отключение функции         | Удаление JAR                               | Удаление кода, пересборка   |
| Тестирование               | Модульное, изолированное                   | Сквозное, сложнее           |
| Риск ошибок                | Локальный, не затрагивает ядро             | Может обрушить всё приложение |
| Порог входа для контрибьюторов | Низкий (реализовать интерфейс Plugin)   | Высокий (разобраться во всём)|

## Заключение

Использование паттерна «Дополнительный модуль» кардинально повышает гибкость, масштабируемость и удобство поддержки приложения.  
На примере нашей Персональной базы знаний видно, что при монолитном подходе всего три встроенные функции уже делают код перегруженным и неудобным для доработки.  
Плагинная архитектура позволяет легко адаптировать программу под конкретные нужды пользователя, не превращая её в «кашу» из слабосвязанных компонентов.
